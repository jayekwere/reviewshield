# ReviewShield threat model

## Overview

ReviewShield provides an offline SARIF evaluator, a separately started signed webhook receiver, a durable receipt queue, a trusted Node queue worker and a credential-free Python static scanner. The queue worker coordinates native GitHub reads and publishes checks in the same privileged process. The separate restricted Docker process scans source without App credentials. Default npm and web-container startup serve only the offline evaluator. Independent fresh-context read-only architecture reviews informed this model; they do not constitute a vulnerability audit or live App acceptance.

## Threat Model, Trust Boundaries, and Assumptions

Protected assets include the App key, webhook secret, installation token, bindings, receipt state, exact source identity, scanner evidence, baseline authority and check integrity. PR authors control source, paths and scanner-visible text, but are not trusted artifact producers or host operators. Reachable clients can send evaluator/webhook requests. The host, Docker client/daemon, selected image, trusted rule pack, private files and maintainers are trusted. Offline tenant labels are data, not logins. A host owner's existing authority is outside the isolation boundary (`SECURITY.md:6`).

The receiver authenticates original bytes before parsing and preserves installation ID, repository ID/name, PR, head SHA and signed payload hash. The queue uses payload-hash uniqueness and a conditional queued-to-processing transition. The separate ReplayStore export is not the receiver's persistence consumer. Worker binding selection must still match all queued IDs. Legacy receipts without numeric IDs fail validation (`src/github.ts:30`, `src/github.ts:51`, `src/app.ts:11`, `src/app.ts:46`, `src/app.ts:52`, `src/app.ts:142`).

Coordination and publication share one privileged Node process. The scanner alone crosses a restricted process boundary. The coordinator fetches an open PR, enumerates up to 500 changed files, rejects incomplete/duplicate enumeration and selects non-deleted .py files. It verifies native Git blob SHA-1 and bytes, computes source SHA-256, validates complete diff hunks and rejects malformed UTF-8. These checks rely on authenticated GitHub responses and the trusted worker; they are not independent cryptographic attestation of a scanner (`src/coordinator.ts:41`, `src/coordinator.ts:242`, `src/coordinator.ts:253`, `src/coordinator.ts:266`, `src/coordinator.ts:292`).

The coordinator transfers bounded file paths, base64 bytes and hashes over Docker stdin. It does not mount host source, keys or the Docker socket in the scanner. The Python worker validates the manifest, copies bounded Python files into a clean tree, excludes PR-controlled ignore/configuration files and rejects symlinks. It never imports or executes target source. Native scanner exit, errors and expected/scanned coverage must all agree. The coordinator separately checks returned hashes and paths against verified blobs, then constructs the review envelope itself (`src/coordinator.ts:153`, `src/coordinator.ts:169`, `scanner/worker.py:19`, `scanner/worker.py:73`, `scanner/worker.py:124`, `src/coordinator.ts:311`).

The bundled rule matches direct eval(input(...)) syntax only, without general indirect-flow or complete vulnerability coverage (`policy/semgrep.yml:7`). Scope is full content of selected changed Python files, with added lines governing annotation placement. Fresh off-diff findings still fail. Other languages and deleted files are explicitly unassessed; mixed scope is neutral absent findings, and no Python scope errors without a clean check. Automatic coordination uses an empty baseline. The separate trusted-artifact workflow can import supported Semgrep/CodeQL SARIF with exact-source, severity, expiry and tenant/repository baseline checks (`src/coordinator.ts:271`, `src/coordinator.ts:323`, `src/review.ts:165`, `src/review.ts:235`, `src/review.ts:272`).

Semgrep stdout/stderr are buffered before post-run 8 MiB stdout/SARIF acceptance checks; stderr has no independent byte cap. The Docker process has a 180-second deadline and host-side maxBuffer. Container memory/CPU/PID restrictions are separate controls. The image alone does not enforce the invocation flags. Host-run legacy scanning inherits its environment and does not supply the same container boundary (`scanner/worker.py:95`, `scanner/worker.py:114`, `scanner/worker.py:117`, `src/coordinator.ts:195`, `scanner/scan.py:35`).

runJob independently rechecks the current open PR head/base and numeric base repository before publish rechecks repository identity and sends checks. Exported publish callers do not automatically get runJob's queue/live-PR checks. The advanced publish command accepts only operator-trusted input and can be repeated. Public SARIF submitted directly to the local evaluator remains a producer assertion, not an authorized check write (`src/app.ts:69`, `src/app.ts:108`, `src/app.ts:180`, `src/github.ts:125`).

Failed work is not automatically retried; crashes can leave processing status and require investigation. Queue completion is not a distributed transaction. Native writes can be partial or duplicated after ambiguous failure, and the worker conservatively reports uncertainty once runJob starts. A returned check ID is not independent readback of every annotation. Scan evidence is printed for operator retention rather than durably stored with each receipt (`src/app.ts:58`, `src/app.ts:157`, `src/app.ts:160`, `src/app.ts:167`, `src/github.ts:162`).

Actual native PR/file/blob reads and the real restricted scanner were exercised on unsafe/safe revisions, including stale-head rejection. Those tests used synthetic local receipts and the existing GitHub CLI session for reads only. Registration, installation, signed live App delivery, installation-token writes and independent check-content readback remain unverified. Persistent hosting and required-check branch protection are operator responsibilities (`docs/live-read-verification.json:2`, `docs/scan-worker.md:23`).

## Severity Calibration (Critical, High, Medium, Low)

Critical requires a concrete route to broad App or host authority. High applies to reachable authentication, installation-binding or privileged evidence-boundary bypasses that confer new authority. Medium covers constrained review deception, confidentiality or availability effects with actual prerequisites. Low covers operational or presentation defects without new privileged capability. Existing trusted host/producer authority is not an attacker privilege gain. Missing live account evidence must not become either a security guarantee or an asserted vulnerability.
